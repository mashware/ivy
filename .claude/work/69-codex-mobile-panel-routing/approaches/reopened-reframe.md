# Reopened M design: give each Ivy console its own Codex daemon

The premise that a generic per-thread `config` override is the only joint-support route is too narrow. A different candidate is a console-scoped Codex home/daemon: ordinary `codex` and `codex resume` in each Ivy console attach to that console's daemon, while that daemon owns the same live thread later opened by remote control. Its Ivy MCP entry would resolve `PANEL_ID`/`PANEL_DIR` for that console. This keeps two consoles from sharing one MCP identity and avoids the second-writer topology reported in the ticket.

Relevant seams are `crates/panel-control/src/bin/ivy-codex.rs` (launch classification and argv), `crates/app/src/shell_integration.rs` (per-console launcher installation), Codex forwarding guidance in `crates/app/src/chrome/connection.rs`, and recovery constraints in `integrations/session-recovery/README.md` plus `crates/app/src/ai_sessions`. The current launcher deliberately adds `--no-daemon`; replacing that policy needs coordinated launch, Connect/setup-prompt and recovery work.

This is a research direction, not a supported solution. Per-console homes can duplicate or diverge user config, auth, plugins and trust; remote-control discovery may expose separate hosts or fail to attach to those daemons; resume/fork/recovery and MCP env inheritance may still bind identity incorrectly. A shared daemon with thread-to-panel routing through an Ivy broker is another conceptual route, but the inspected evidence does not show Codex supplying a stable thread key to MCP calls. Either approach risks regressions in the independent-session behavior introduced by #43/#46. Validate exact-version lifecycle and real two-console plus phone behavior before changing the launcher. A connected remote server remains insufficient evidence.
