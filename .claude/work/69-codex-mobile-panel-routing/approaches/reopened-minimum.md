# Reopened minimum approach

Keep `ivy-codex`'s `--no-daemon` safeguard until a target-version runtime experiment proves that invocation-scoped MCP identity can coexist with one daemon-backed conversation. The smallest candidate is to add temporary `-c mcp_servers.<existing-name>.env...` overrides to ordinary start/resume invocations, deriving values from that console's `PANEL_ID` and `PANEL_DIR`; do not persist config or print values. Do not assume overrides work: the schema's generic `config` field and help are not propagation evidence.

First, use Codex 0.167.0 (and the owner version if different) with a disposable config and a test MCP server that records opaque panel markers. Verify CLI parsing, whether daemon-side MCP calls receive the invocation's values, what happens when two consoles use the same configured server name concurrently, and whether resume/fork and phone reattachment preserve the right mapping. Check config bytes before and after. If a shared daemon cannot hold distinct identities, test the smallest supported per-thread/server mechanism before considering topology changes; do not create separate homes or proxies without documented mobile attachment and recovery behavior.

Only if this passes, make a narrowly scoped wrapper change and test two live Ivy consoles (start and resume; cross-panel markers never appear), plus a real phone opening each active thread, loading history, sending input, and observing no active-writer error. Include explicit remote launch and alias/function regressions. Otherwise retain launch policy and update README, Connect guide, and copied setup prompt with the verified limitation and supported choices. A `connected` server status is not success evidence.
