### Measured results (synthetic identities only)
1. **Direct protocol is a viable primitive.** `python3 /tmp/ivy69-research/direct-probe.py` started one stdio app-server, initialized experimental API and created A/B threads using dotted config key `mcp_servers.ivy`, whose value contains a Python stdio MCP command and env. `mcpServer/tool/call` returned console-A then console-B. Both threads were alive in the same app-server process when called. Saved replies: probes/direct-results.json; fake MCP: probes/mcp-env.py. This proves tool identity propagation in the direct protocol; it does not prove real Ivy panels or mobile use.
2. **Explicit remote CLI drops these overrides.** A loopback WebSocket adapter forwarded the real CLI's messages to an isolated real stdio app-server. `codex --remote ws://127.0.0.1:18769 -c mcp_servers.ivy.command=... -c mcp_servers.ivy.env.PANEL_ID=... -c mcp_servers.ivy.env.PANEL_DIR=... --no-alt-screen` sent thread/start with config `{}`. Summary: probes/remote-request-summary.json; harness: probes/cli-probe.py and proxy.cjs. No invocation MCP identity reached the server in that request. This is specific to this tested CLI path/version.
3. **Ordinary override success was in-process.** After starting an isolated managed 0.167.0 daemon (PID 1075, subsequently restarted as 1681), ordinary CLI with invocation MCP overrides launched the fake MCP with parent PID equal to the TUI PID (1537), not the managed daemon PID. Removing inherited CI/session marker environment variables did not change that observation. A distinct PANEL_ID from this experiment is therefore not daemon-routing proof.
4. **Discriminating plain vs override test.** In the disposable home only, wrote synthetic MCP config with PANEL_ID=daemon-baseline, features.daemon_auto_start=true and check_for_update_on_startup=false. Restarted only that disposable daemon. Plain CLI `codex --no-alt-screen` (TUI PID 1730) launched MCP under managed daemon PID 1681, with daemon-baseline. Then the same CLI plus only `-c mcp_servers.ivy.env.PANEL_ID="console-override"` was tested separately; see probes/ordinary-summary.json. This controls for the earlier multi-override command. Never apply this synthetic persistent identity configuration to a real Ivy install.
5. **Resume not established.** An additional direct thread/resume on an empty pre-turn thread returned `no rollout found for thread id ...`. That probe ended nonzero after both successful identity calls. No saved-turn history was created, and no model turn was requested. This failure proves neither resume rebinding nor an upstream writer bug. The first direct-probe attempt also failed because its disposable home was missing; after creating it, the identity experiment passed. App-server proxy newline-RPC experiment timed out; its transport assumptions remain unverified and it is not evidence of a product limitation.
