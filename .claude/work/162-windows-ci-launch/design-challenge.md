| Angle | Finding | Type | Severity | Response proposed |
|---|---|---|---|---|
| Omission reporting | The design requires one exact name/count report from Cargo's compiled harnesses, but proposes same-named ignored counterparts and leaves the aggregator unspecified. Cargo output is per test binary; parsing human `... ignored` lines is format-sensitive, while counts alone cannot establish names/reasons or detect an accidental added omission. The repo's existing PowerShell witness step already parses pretty test output, so this is a real maintenance seam. | Fragile assumption | High | Author decision needed: accept a version-pinned parser over `--list`/normal test output, or add a deliberate machine-readable inventory/report mechanism. Define the invariant that reported names equal compiled ignored counterparts, not merely a summed ignored count. |
| Default shell fidelity | External GUI input is faithful to the user's route into the console, but only if the smoke leaves shell selection inputs untouched (except required removal of `SHELL`) and proves which child executable handled the command. `shell_integration.rs` already tests Windows selection and runs commands through PTY for default/fallback; the GUI smoke adds installed startup and UI input integration, not shell-selection coverage by itself. A command/file marker without process identity could pass through an unexpected shell. | Coverage gap | Medium | Keep external input, but have the witness establish the spawned shell identity (or otherwise bind it to the existing resolver) and use a command valid for the resolved shell. State whether inherited `PATH`/`COMSPEC` is intentionally part of the default behavior. |
| Smoke scope | Requiring a native window, console output, persisted layout and normal exit is well aligned with the reported installed-launch failure and existing `session.rs` APPDATA fallback. Building/installing on PRs is necessary to exercise the shipped path; the manual release job cannot supply that evidence. | Fit | Low | Retain. Keep release publication gated and make PR installation consume a candidate artifact so the new check does not duplicate the binary build. |
| Automation operations | PID-targeted GUI automation can still race window creation/focus or be blocked by modal first-run dialogs; a fixed delay would be brittle. The design already calls for bounded waits and diagnostics, which is the right direction, but the launch contract should say what window/dialog state counts as startup and how failure preserves evidence before tree cleanup. | Operations | Medium | Use window discovery by launched PID and title/class, wait on state rather than sleeps, capture window/process diagnostics before timeout cleanup. Explicitly decide whether unexpected dialogs fail immediately. |
| ADR rationale | The ADR rejects a static manifest because it can drift, yet ignored counterparts also require maintaining one per omitted behavior and add inert test declarations. The difference is defensible only if the harness guarantees their presence and reportability. | ADR rationale | Medium | Clarify that the advantage is compiler-verified per-target visibility and that CI checks every expected omission name; otherwise prefer the simpler checked-in manifest tied to the test audit. |
