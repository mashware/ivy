Use a Linux-only launch helper as the child tracked by `Pty`, with a startup gate. It inherits the PTY, cwd, and final environment; argv carries the original program and arguments, so it can `exec` the target in place and preserve pid/PTY semantics. Before releasing the gate, the parent asks the user manager over D-Bus to create a transient scope containing the helper PID, then waits for the unit job result. If no manager exists or setup fails, release the helper into the original program as fallback. Keep `try_wait` and HUP/KILL cleanup against this pid; scope cleanup may also stop the unit to contain descendants.

Do not spawn the real program and attach later: it can fork first. `portable-pty` 0.9 `CommandBuilder` has no public `pre_exec` hook; Unix uses `std::process::Command::pre_exec` internally. A blocking pre-exec gate prevents `spawn` from returning, so it cannot coordinate the parent. The helper must wait on a separate control channel before `exec`; pass OS strings directly to preserve non-UTF-8 argv. The target inherits the configured environment unchanged.

Track the unit name and query its final systemd result after the child ends. Add an OOM notice only for an explicit OOM result (or observed cgroup `oom_kill` evidence); bare `SIGKILL` is ambiguous and stays generic. Keep the existing output/ending channel and app notice path. macOS/Windows remain unchanged.
