# Security challenge

| Finding | Severity | Recommended response |
|---|---|---|
| No unresolved high-severity flaw found within the stated same-user trust boundary. The design closes the main cross-user paths: directory creation is secured at birth and revalidated through a no-follow handle; pipe ACL is explicit; first-instance creation rejects a preexisting name; and clients authenticate the connected server PID before sending bytes. | — | Keep these checks in the shared entry paths, including direct `Producer::of`; test both inherited and explicit construction paths. |
| Remote-client rejection has weaker proof than the rest of AC2. The plan says to assert the construction mode and run a native remote test “where available.” Inspecting the flag passed by the implementation does not prove that the created pipe rejects remote clients, and a runner without remote reachability cannot satisfy that behavior criterion. | Medium, proof gap | Make a remote connection test a required Windows CI/manual gate on a network-capable host, or mark AC2 incomplete until one runs. Keep `PIPE_REJECT_REMOTE_CLIENTS` on every instance and the actual pipe DACL inspection regardless. |
| Directory and pipe ACL descriptions say “only expected” user/SYSTEM ACEs but do not spell out accepted masks and inheritance flags. A future validator could accept an unexpected ACE shape while still matching those SIDs. | Low, implementation ambiguity | Define exact ACE types, masks, and flags for both objects; assert descriptor protection and exact ACE tuples from the actual handles. Include null DACL, inherited ACE, extra allow ACE, and broad generic-rights fixtures. |

The PID is a routing/authentication witness against a different app instance, not a credential against another process of the same user; the design states that boundary correctly. The planned actual-handle `GetSecurityInfo` plus `AccessCheck` using a distinct-user token is credible evidence for cross-user denial. A same-user denial test would be incorrect and should not be added.
