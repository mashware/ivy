## Reframe: a small Windows transport adapter

The ticket’s security requirements do not imply replacing the channel or its worker model. Keep the existing blocking `Stream` protocol and per-connection workers on POSIX; on Windows, add a narrow native adapter around `CreateNamedPipeW`/`CreateFileW`, exposed through the endpoint’s current bind/connect seam. Build each server instance with an explicit security descriptor granting only the current user and SYSTEM, `PIPE_REJECT_REMOTE_CLIENTS`, and `FILE_FLAG_FIRST_PIPE_INSTANCE`. Use overlapped `ConnectNamedPipe` with a private manual-reset stop event; wait on the connect event and stop event, cancel pending I/O on shutdown, then join the acceptor. Before serving a connected handle, compare `GetNamedPipeClientProcessId` with the inherited app PID. Keep the existing eight-connection cap and bounded read/stop behavior, adapting the pipe handle to the existing framing/handler boundary.

Affected layers: `endpoint.rs` for bind/connect and handle ownership; `listener.rs` for Windows accept readiness, stream I/O and shutdown; peer capture/client connection types; Windows-specific tests that inspect the pipe DACL, remote rejection, first-instance collision, PID mismatch and drop bound. The MCP and wire protocol layers should remain transport-agnostic.

This deliberately challenges treating interprocess 2.4’s common `Listener`/`Stream` surface as sufficient: the acceptance criteria require native creation flags, an asserted DACL, client PID attestation and overlapped cancellation that a portable blocking abstraction may not expose. Risk: handwritten Win32 handle/ACL/overlapped code is easy to get subtly wrong and needs real Windows CI. Why it may be a bad idea: it adds a second transport implementation and platform-only security code, raising maintenance and review burden; adopting an async runtime or rewriting all workers would be worse scope without improving these guarantees.
