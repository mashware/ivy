# Windows transport boundary

`listener.rs` and `client.rs` directly name `interprocess::local_socket::Stream`; peer capture destructures it as `UdSocket`. Add an internal `TransportStream` with Windows owned-handle and POSIX interprocess variants, implementing `Read`/`Write`, clone/refusal behavior, and existing timeout calls. `Listener`/`Acceptor` also need platform adapters; retain Unix poll + wake-pair behavior. Windows handles use `FILE_FLAG_OVERLAPPED`. Each operation owns its `OVERLAPPED`, event and buffer until completion is drained: on stop/deadline call `CancelIoEx`, then reap completion before freeing state or closing the handle. Abandoning an in-flight write after signaling stop risks invalid state. `Channel::Drop` sets stop, signals the acceptor and detaches; it intentionally does not join, so each connection must cancel and clean up independently.

The ticket’s expected **server** PID is the pane process. Add a dedicated inherited value (e.g. `PANEL_APP_PID`) at the common pane environment source in `panel-contract`, propagate it through child launches, and have Windows `connect` compare `GetNamedPipeServerProcessId` with that value before returning a producer. This differs from accepted-client peer capture (`GetNamedPipeClientProcessId`), which Windows session/publisher authorization needs; diagnostic classification can remain unavailable unless required.

Transport cancellation does not solve the release wrinkle: teardown uses blocking `to_the_window.send(Closed)`, while publications use `try_send`. A full inbox can keep a detached worker alive until the UI drains it or drops the receiver. Meeting “drop bound and no worker” needs a bounded release policy or a narrower criterion, regardless of transport. Windows checks should cover actual DACL, cancellation/worker exit, server PID mismatch, remote rejection and first-instance collision.
